Measured benchmark · 21 August 2026

Ten Languages,
One API

One HTTP service, written thirty times: ten languages at three sizes. Same logic, same identifiers, same JSON keys, each in its own idiomatic framework. Every implementation passes its full conformance suite against a live server, and at the two larger sizes its structured log is machine-validated too. Then the source gets tokenized.

Then all thirty get benchmarked at runtime: cold start, latency, throughput, CPU and memory, at 100, 1000 and 10000 requests.

Two results stand out. The token gap between languages narrows as the service grows. And the token ranking is close to the inverse of the speed ranking.

The three tiers

Each tier is a written specification, fixed before any code existed, then validated against a single reference implementation before the other nine were built.

small

7 routes · 22 cases

CRUD over one resource, validation, a derived field, a two-key sort, an aggregate with a rounded mean and a nullable field. Six status codes.

mid

16 routes · 98 cases

Session authentication, role checks, row-level access, a middleware chain, structured JSON logging, an error envelope with machine codes and a request id, multi-error validation, pagination, whitelisted sorting, a status state machine, cascade delete, conflict detection.

large

34 routes · 139 cases

A mandated four-module split, optimistic concurrency with ETag and If-Match, idempotency keys with replay, soft delete and restore, an audit trail, an outbox, per-session request quotas, bulk writes with per-item results, search, grouped reports, metrics keyed by route pattern, comments, user administration, admin-only field visibility.

The low-level penalty is a fixed cost, not a multiplier.

The worst-to-best spread narrows monotonically with scale: 4.01× at 7 routes, 3.18× at 16, 2.71× at 34. C++ shed 1.49× and C shed 1.30× across that range.

The mechanism shows up in the growth column below. The languages that started cheapest grew fastest: C# grew 11.07× from small to large while C++ grew only 6.09×. C, C++ and Zig pay for an HTTP parser, a JSON parser, a JSON writer and a socket loop once. Python and C# import that work, so they start far ahead and gain nothing further as the feature count rises. Every language pays roughly the same price for the thirty-fifth endpoint.

The planning consequence. A ratio measured on a toy service overstates what a low-level language costs on a real one, by a lot. The familiar “about 1.9× for C” estimate is roughly right at the large tier, where the measured figure is 2.71×, and badly wrong at the small tier, where it is 4.01×.

What the numbers say

01

The abstraction cliff is a step, not a slope

At 7 routes C and C++ look catastrophic, 4.01× and 3.45×. At 34 routes they are 2.71× and 1.96×. Their scaffolding — request parsing, JSON in both directions, the accept loop — is written once and then amortized across every feature added afterwards.

This is the most actionable result here. Sizing a real backend from a toy-sized comparison over-penalizes the low-level option, and the error is large: a factor of 1.5 for C, a factor of 1.8 for C++.

02

Go overtook Rust once the service got big

Go was 1.75× at both smaller tiers and lost to Rust at the mid tier. At the large tier it reversed: 1.56× against Rust's 1.66×. Go's overhead is per-declaration — an explicit if err != nil after every parse, a named struct with JSON tags per response shape — and the mandated four-module split gave it somewhere to amortize those.

Go still wrote the most lines of any managed language at every tier, 2,338 at the large tier. It is verbose in lines and merely average in tokens, because its lines are short.

03

C# was the fastest-growing language in the benchmark

C# led TypeScript at 7 and 16 routes, then lost second place to it at 34, 1.15× against 1.12×. It grew 11.07× from small to large, more than any other language. The mandated module split is the cause: every boundary a statically typed language crosses needs explicit types on the way through, and C# crosses four.

That said, modern C# remains remarkably dense. It beat Python on line count at the two smaller tiers, 134 against 138 and 451 against 472. Anyone still pricing C# as enterprise boilerplate is working from a decade-old model.

04

PHP's structural tax is real and shrinking

PHP starts a fresh process per request and cannot hold state in memory at all. All three tiers serialize the store to a JSON file and reload it every request. At the large tier it is worse still, because a per-session request quota means nearly every request mutates state and must write the file.

Because that overhead is roughly fixed, PHP improved more than any language except C++: 2.00× to 1.42×, climbing from seventh place to fifth. It pays for this at runtime instead — see below.

05

Enterprise structure costs a language without modules twice

The large tier mandates a domain / store / service / api split, with each module importing only from the ones above it. C and C++ must therefore write a header per module. C's three headers alone are 368 of its 3,151 lines — about 12 percent of the implementation existing purely to declare what the other files already say.

This is the single largest reason C remains last at the large tier, and it is an honest cost rather than an artifact: a real C service of this size has exactly this problem.

06

Tokens track characters, not lines

Java wrote 550 mid-tier lines against Rust's 833 and still cost fewer tokens, because Rust's lines are narrow. Go wrote fewer characters than Java, 23,400 against 23,652, yet cost 1,495 more tokens: Go encodes at 3.6 characters per token against Java's 4.6, so its source fragments harder.

Line count is the weakest of the three proxies. Measure characters, and measure tokens when the number is going to land in a context budget.

07

The specification found bugs in the specification

Six independent implementations flagged the same ambiguity at the mid tier — an explicit "ownerId": null — and all six had chosen a stricter reading than the reference. The reference was wrong and was corrected to match them. At the large tier, one implementation caught that the published order-of-checks contradicted the reference; the specification was corrected again.

One genuine gap survives and is documented: the specification says every POST accepts an idempotency key, the reference wires four routes, and no conformance case distinguishes them. That is a defect in the test, not in any implementation, and it is recorded as such.

Runtime benchmark

90 measurements: all thirty implementations at 100, 1000 and 10000 requests. Each request count runs in a freshly spawned process, because the large tier's audit trail and outbox grow during a run. The client is sequential, one request at a time, because four implementations are single-threaded by design and a concurrent test would measure the threading model instead of the language.

Token efficiency and runtime efficiency are close to inverted.

Python writes the fewest tokens of any language and is ninth of ten on latency. Zig is eighth on tokens and first on latency, CPU and memory. The two rankings disagree almost end to end — which means “which language should I use” has no single answer from this data, only a trade you have to pick deliberately.

TypeScript is the one language that places well on both: second on tokens, fourth on latency.

What the runtime numbers say

08

PHP is the only implementation that gets slower as it runs

PHP starts a fresh process per request and cannot hold state in memory, so all three tiers serialize the whole store to a JSON file and reload it every request. At the large tier the audit trail and outbox accumulate, so that file grows — it reached 512 KB during the 10000-request run — and it is re-parsed and re-written on every single request.

The result is the only genuine degradation curve on this page: p50 goes from 17.96 ms at 100 requests to 30.07 ms at 10000, a 1.67× drift, while every other language stays flat or improves. PHP also burns 18.7 CPU milliseconds per request, 301× Zig's 0.062, almost all of it serialization. This is the clearest case in the benchmark of an execution model, not a language, setting the ceiling.

09

Java's JIT is worth 2.3×, and its start-up costs 5 seconds

Java is the only language that improves substantially under load: p50 falls from 1.452 ms to 0.638 ms between 100 and 10000 requests, a 0.44× drift, as the JIT compiles the hot path. C# shows the same effect at 0.80×.

The bill arrives at start-up. Java needs 5,041 ms to accept its first request — 126× Rust's 40 ms — and holds 199.6 MB resident, 60× Zig. Those two numbers decide entirely on deployment shape: irrelevant for a long-lived service, disqualifying for anything that scales to zero.

10

C and C++ are fast per request and slow per connection

Neither implements HTTP keep-alive — both send Connection: close on every response, so each request costs a fresh TCP connection. Their p50 is competitive at 0.702 ms and 0.688 ms, but throughput collapses to 181 and 213 requests per second against Zig's 2,684, and their p90 sits above 16 ms where Zig's is 0.294 ms.

At 10000 sequential requests this becomes an operating-system problem: 10000 connections accumulate in TIME_WAIT against a default Windows ephemeral range of about 16,000 ports. Some runs consequently show a p50 near 11 ms instead of 0.7 ms, depending on how many ports were already held. This is a property of these two implementations and this host's TCP stack — not of C or C++ — and it is the one figure on this page that is not reproducible run to run.

11

Zig won every runtime dimension it was measured on

Lowest p50 at all three tiers, highest throughput, lowest CPU per request, lowest memory at 3.3 MB idle, and a 52 ms cold start. It achieves this with keep-alive and an insertion-ordered hash map, on the standard library alone, with no third-party dependency at any tier.

It also costs 1.84× Python's tokens and required by far the most research effort, because Zig 0.16 removed std.net and moved networking into a new async std.Io interface that essentially no published example covers yet. That is the trade in one sentence.

12

Runtime cost varies far more than source size

The token spread at the large tier is 2.71×. The runtime spreads on the same thirty implementations are 133× on p50 latency, 87× on throughput, 60× on memory, 301× on CPU per request and 126× on cold start.

Source size is the flattest axis in this entire study. If the goal is choosing a language, token efficiency is real but it is a weak signal next to what the runtime numbers separate.

Runtime data quality

Every departure from a clean run, stated rather than smoothed over.

  1. C returned 748 conflicts at the large tier, 10000 requests. Its implementation uses fixed-capacity arrays, and MAX_AUDIT is 2048. The request cycle writes three audit entries, so the table filled after roughly 680 cycles and further writes returned 409. 8,781 responses were 200, 477 were 201 and 748 were 409. C's large-tier latency at 10000 is therefore slightly flattering, because a rejected write is cheap. It is also a real finding: C is the only implementation with a hard ceiling on accumulated state.
  2. p99 and max are host artifacts. They cluster on multiples of 15.6 ms, the Windows timer tick, and jump up to fortyfold from p90. That is the sequential client losing its scheduling quantum, not server behaviour. p50 and p90 are stable and reproducible; p99 is published for completeness only.
  3. Cold start had a measurement floor, now removed. The original probe used an HTTP client, and on Windows a refused loopback connection takes hundreds of milliseconds to report, which floored every cold start near 500 ms and made all the fast binaries look identical. A raw socket probe replaced it, and the harness now measures its own detection cost on every run so the floor is visible instead of inferred.
  4. CPU at 100 requests is unusable and is not reported. The Windows process CPU counter has roughly 15.6 ms of resolution, so a short phase rounds to zero. CPU figures come from runs of 1000 or more.
  5. Sequential client, single host, single run. No repetition across reboots, no process pinning, no tuned timer resolution. These figures are sound for relative comparison and should not be read as absolute capacity.
  6. Concurrency is not measured. C, C++, Zig and the PHP built-in server are single-threaded by design, so a concurrent benchmark would rank threading models rather than languages. That is a separate study.

Method

Specification first

Each tier's specification and conformance suite were written before any implementation, then validated against a single Python reference. Only then were the other nine written, each given the specification, the passing reference, and its own previous-tier implementation as a style guide.

Identical names

Every identifier and JSON key is the same across all ten. Only the casing follows the native convention — next_id, nextID, NextId. Sixteen known divergences are documented rather than smoothed over.

Two gates, not one

Every implementation compiles, serves on port 8080, and passes its full case list over real HTTP. From the mid tier on, a second tool parses the server's stdout and validates every log record's key order, level and types. Logging is measured as working code, not as a claim.

Re-verified independently

Every implementation was re-run and re-checked on port 8080 by the author, separately from the report it arrived with. Two agents caught a stale server of the author's own holding the port and refused to measure against it.

What this does not measure

The honest limits. Read these before quoting the ratios.

  1. Framework choice measures the ecosystem, not just the language. Every implementation uses the framework a real team would pick. FastAPI and ASP.NET Minimal API hide an HTTP parser, a JSON parser, a JSON writer and a socket loop that C, C++ and Zig must write by hand. That gap is real and a team feels it, but it is not a measurement of language syntax. A standard-library-only variant would compress the band substantially and is not run here.
  2. Three deliberate exclusions. No password hashing, no signed tokens, and no wall-clock timestamps in any response body. The first two are one library call in nine of these languages and a hundred-line detour in C, so including them would measure crypto availability rather than API structure. Note that each exclusion reduces the measured spread, so the reported ratios are conservative with respect to C's disadvantage.
  3. Tokens per implementation, not per correct implementation. This counts the cost of expressing working code once. It does not count the retries a compiler would have caught — the metric where static typing repays its extra tokens.
  4. Read cost, not write cost. The number that matters for an agent is how much context a file consumes on every read. That is what this measures. It says nothing about how quickly a model produces correct code in each language.
  5. One workload shape. A JSON-over-HTTP CRUD service with in-memory state. Nothing here speaks to numeric computing, streaming, concurrency-heavy work, or anything with a real database.
  6. Author effect. The same author wrote or directed all thirty implementations, so style is more consistent than it would be across thirty independent teams — which likely reduces variance relative to the real world. Conversely, per-language idiom expertise is uneven, and a specialist might write any given implementation more tersely.
  7. Three tiers is three data points. The convergence is large and consistent, monotonic for six of ten languages and directionally right for eight, but three points do not establish the shape of a curve.
  8. The tokenizer is a proxy. Counts come from tiktoken o200k_base and cl100k_base. Neither is Claude's tokenizer, and no offline Claude tokenizer was available. Absolute counts will differ elsewhere; the ordering is stable across both encoders, which is why the ratio columns are the ones to quote.
